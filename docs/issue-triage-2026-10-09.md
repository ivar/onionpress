### 2.4 Security findings (not tracked by an open issue)

Found while checking #126 and #60, verified in `app/Resources/docker/tor/web-server.py` and `entrypoint.sh` on `brewster/main`:

1. **Signature verification is skipped for every onion caller.** `is_local_request()` (web-server.py:329-339) returns true for `127.0.0.1`, and the file's own comment (lines 834-837) notes that Tor forwards onion-service connections from `127.0.0.1`. `_verify_signature()` therefore returns ok without checking for `/online`, `/offline` and `/unregister` whenever the caller comes in over Tor, unless `ONIONHEAVEN_ENFORCE_AUTH=1` (set only in `tests/test_onionheaven_integration.py`). The key-to-address derivation check at web-server.py:1036-1053 still limits what `/online` can do, but `/offline` and `/unregister` for any registered address are open.
2. **`POST /reset-onionheaven` has no auth and no network restriction** (web-server.py:633-644, 1252-1261), and port 8083 is published on every node's wordpress onion (`entrypoint.sh:257`). The handler runs `docker exec` through the mounted docker socket. `register-local`/`release-local` already have the Docker-bridge-only guard (web-server.py:841); reset should get the same, or be removed from the public dispatch table.

Suggested fix is one small PR: drop `127.0.0.1`/`::1` from `is_local_request`, gate `/reset-onionheaven` behind the bridge-only check, and add a test that an onion-origin request without a signature is rejected.

## 4. Notes for maintainers

- **Arti is gone** (v2.5.0, [5d234cf7](https://github.com/brewsterkahle/onionpress/commit/5d234cf73d6c68f5b72fff6217c1f1ca9a84ab42)); none of the open issues is Arti-specific, but PR #274 (attached to #277) and the prose in #236/#80/#154/#194 still mention it. `tests/arti-*` leftovers are build-script territory, not issue territory.
- **Linux parity is the recurring theme**: #207 (no analytics upload), #203 (inline backup bash), #198 (no thumbnails), #144 (no clearnet logging), #116 (actually better on Linux). A single "Linux delegates to `onionpress.cli`" PR would retire most of them.
- **Hub hygiene cluster**: #232, #126 (+ section 2.4), #60, #74, #77, #57 all touch `app/Resources/docker/tor/web-server.py` / `onionheaven_common.py` and are each small; one focused PR could close four of them.
- **Stale code noticed while checking, no issue filed**: `app/Resources/plugins/onionpress-settings.php:703,965-966` still offers a "Tor Implementation (advanced)" Arti/C Tor select although `TOR_IMPL` was removed (and `tests/test_install_invariants.py:140` forbids it coming back); the Linux self-update path copies two files that no longer exist (`linux/onionpress:2726-2727`); `app/MacOS/onionpress:2205` `restore_backup()` is never called.
