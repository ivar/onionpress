# Manual testing and test gaps: #527 and #528

Covers [brewsterkahle/onionpress#550](https://github.com/brewsterkahle/onionpress/pull/550) (#527, merged 2026-11-03 as [dd2f571d](https://github.com/brewsterkahle/onionpress/commit/dd2f571d29777088c31b7a5234086c90eb9ded9a)) and [brewsterkahle/onionpress#552](https://github.com/brewsterkahle/onionpress/pull/552) (#528, all six items, merged 2026-11-03 as [ceadac42](https://github.com/brewsterkahle/onionpress/commit/ceadac426927b46b5223daedcbe94face3fb4c97)). Both are on upstream `main` (tip ceadac42, with [brewsterkahle/onionpress#553](https://github.com/brewsterkahle/onionpress/pull/553)'s e2e changes between them). Neither is in a release yet: v2.6.1 is the latest.

Every check below was only ever run as unit tests with Docker, the browsers, archive.org and OnionHome stubbed. Nothing was run on a real Mac or Linux install.

**How to get a build under test:** build the DMG from upstream `main` at ceadac42 or later (`make build`) and the .deb (`build/build-linux.sh`). The PHP plugins ship with the app: every start's `provision-post-install` copies them into the container, so no image publish is needed for them. The one exception is `onionpress-security-audit.sh` (#528 item 6), which is in the WordPress image: use `make images` and `ONIONPRESS_WORDPRESS_IMAGE`, or skip that check. Use throwaway installs (a scratch data dir or the `/tmp/opqa` recipe), never the live `~/.onionpress`.

## Part 1: manual checklist

### Found while writing this (check first)

- [ ] **The e2e suite and OnionHome: fixed in [brewsterkahle/onionpress#554](https://github.com/brewsterkahle/onionpress/pull/554) (open).** Since #550 every e2e t0 run registered its test onionname with the real OnionHome: setup registers it, and the daemon on both platforms retries any unregistered name once Tor is up. #554 makes registration use the config's `ONIONHOME_ADDRESS` (empty means none, as analytics sharing already reads it); the e2e baseline config sets it empty. Check on the next e2e run: the name stays unregistered and the tripwire stays clean. Open question, unchanged: should opting out of OnionHeaven also skip onionname registration?
- [ ] **`--register-later` on both platforms:** the daemon registers the name once Tor is up (not only on a Mac). Check that it does on Linux, and that a collision found then reaches the tray.

### #527: first run on a Mac (setup window)

- [ ] **Fresh install, end to end:**
  - [ ] The setup window shows `setup --json`'s progress lines as they come.
  - [ ] WordPress is installed under the onionname.
  - [ ] The browser opens on the site when it is ready.
  - [ ] `.setup_complete` and `.wordpress-installed-by-onionpress` are written.
- [ ] **Language:** choose a non-English language (for example `fr_FR`); the admin is in that language.
- [ ] **Taken onionname:** a name already registered with OnionHome.
  - [ ] Nothing is installed.
  - [ ] The collision dialog shows the suggestions.
  - [ ] Choosing one installs under it.
- [ ] **"Skip for now":**
  - [ ] Installs with the name recorded unregistered (`ONIONNAME_REGISTERED` not yes).
  - [ ] The daemon later registers it, or reports a collision.
- [ ] **Password handling:** the password never appears in `ps` (check during setup) or in `launcher.log` / `onionpress.log`.
- [ ] **The Tor start race:** the daemon starts Tor once WordPress is installed while `setup` may also start it at its end. Check `docker ps` for one tor container and no restart loop.
- [ ] **Archive.org keys after setup:** the detached `ensure-archive-s3-keys` runs and the keys land in the main site's options (`wp option get onionpress_archive_s3_access`).

### #527: first run on Linux (tray)

- [ ] **Fresh .deb install:** the tray's setup dialog completes through `setup --json`.
- [ ] **New on Linux: the onionname is registered with OnionHome at setup.** Check the config's `ONIONNAME_REGISTERED` and OnionHome's answer.
- [ ] **Taken name:** the tray asks for another name and runs the setup again.
- [ ] **The tray's legacy branch (a WordPress the start installed):**
  - [ ] It runs `provision --json`.
  - [ ] A WordPress OnionPress did not install is refused (#464), unless `--adopt-existing`.
- [ ] **Regression check:** before #550 (v2.6.1 is not affected; it came with #541), the tray's first-run setup and every logged-in Open raised `TypeError`. Confirm both now work.

### #527: opening the site logged in

- [ ] **Mac, Tor Browser installed:** "Open in Tor Browser" opens the `file://…/OnionPress/.auto-login/login-*.html` page, which redirects to the `.onion` logged in. This path is new on the Mac (LaunchServices is no longer used).
  - [ ] The folder is 0700 and the page 0600.
  - [ ] The page is gone after use.
- [ ] **Mac, a browser with the extension connected (Chrome or Firefox):** same check.
- [ ] **Mac, Brave:** gets the bare URL, with no token.
- [ ] **Mac, no Tor browser at all:** the menubar shows its install dialog (`no_browser`).
- [ ] **Linux, Tor Browser already running:** the paste dialog with the URL.
- [ ] **Linux, Tor Browser not running:**
  - [ ] A cold launch shows the "starting" notification.
  - [ ] The tab opens once firefox.real is up.
  - [ ] The token is minted only then.
- [ ] **Linux, no torbrowser-launcher:** opens the default browser.
- [ ] **Both:** Open Local Site and Settings… open the right pages; the token is never on any command line (`ps` while opening).

### #527: renaming after a collision

- [ ] **`onionname set NEW --rename-admin` on a real multisite:**
  - [ ] user_login and user_nicename change.
  - [ ] The `site_admins` network option names the new login.
  - [ ] You can log in with the new name.
- [ ] **A taken name:** renames nothing.
- [ ] **Menubar:** the collision dialog after setup (the daemon's report) runs it and shows the result.

### #528: Settings page (Mac and Linux each)

- [ ] **Release line:**
  - [ ] With no check yet: "Check for Updates".
  - [ ] Pressing it: the notice says "Checking for a new release of…", then the latest version.
  - [ ] Reloading: the line shows the cached answer with its time.
  - [ ] It is never a downtime action.
- [ ] **No GitHub request from WordPress:** watch the tor container's or the egress log while the page loads.
- [ ] **Share Now with sharing on:** "Upload queued", and the upload happens within a cycle (the daemon log, the hub's receipt).
- [ ] **Share Now with sharing off:** the refusal message.
- [ ] **Saving a setting:**
  - [ ] The form shows the saved value at once, before the host applies it.
  - [ ] After the next handle-action run, `config-current.json` matches.
- [ ] **Restart prompt (Linux only):** shown for `VM_MEMORY` and the two OnionHeaven tunables; not for the others.
- [ ] **Status page Refresh Now:** re-reads, with no `requested-action` written (check the volume).
- [ ] **Security audit (needs a locally built WordPress image):**
  - [ ] Findings are in the container log as `[security-audit]` lines.
  - [ ] `security-report.txt` is gone.

### #528 item 3: archive.org login from the page

- [ ] **Correct account and password:**
  - [ ] "Logging in to Archive.org from OnionPress…", then "Archive.org credentials saved."
  - [ ] The keys are in the main site's options.
  - [ ] The Wayback sweep submits with them.
- [ ] **Wrong password:**
  - [ ] An error with archive.org's reason.
  - [ ] Neither the password nor the account appears in the notice, `recent-logs.txt` or the host log.
- [ ] **The request file's lifetime:** watch `/var/lib/onionpress/archive-login` (`ls -l` in a loop in the wordpress container).
  - [ ] It is 0600.
  - [ ] It is gone within one daemon cycle.
  - [ ] It is gone before the login request goes out.
- [ ] **Two logins within 30 s:** the second is throttled and its file removed.
- [ ] **Login while another action is pending (for example a restart):** "OnionPress is busy".
- [ ] **New page against an old host** (main's `onionpress-settings.php` copied into a v2.6.1 install's container): the page refuses with "update OnionPress" and writes no file. In normal use the two only disagree until the first start after an update has copied the new plugins in.
- [ ] **A subsite administrator** (not super admin): the fields do nothing.
- [ ] **"Remove the saved credentials":** still clears the keys.

## Part 2: what could be scripted but isn't

Ordered by value.

1. **The e2e harness and onionname registration: fixed in [brewsterkahle/onionpress#554](https://github.com/brewsterkahle/onionpress/pull/554).** t0's `test_no_public_service_contact` now asserts the onionname stayed unregistered. Still missing: a t0 test that a node pointed at its own OnionHome registers there.
2. **`onionpress_request_archive_login` under php.** It is only checked by reading the source. `tests/test_settings_page_results.py` and `tests/test_wayback_network_state.py` already run plugin code under `php` with WordPress functions stubbed. The same harness could check:
   - the file is 0600 and holds the JSON;
   - nothing is written without `page_actions`, or while `requested-action` exists;
   - the request id and `requested-action` are written in order;
   - a failed write leaves no file.
3. **The save handler's archive-login branch under php:** the notice's `data-op-action` and request id, the error notice, and that the password is never in the output.
4. **The launchers' `setup --json` stdout through `main`.** `tests/test_launcher_dispatch_{mac,linux}.py` don't run the `setup` case with `--json`. A row would hold:
   - the JSON answer as stdout's last line;
   - "Setup complete!" and cloudflared's lines on stderr;
   - the exit codes 0, 1, 2 and 10 passed through.
5. **e2e: logged-in open on linux-vm.** `onionpress open onion --json` with no torbrowser-launcher should answer and open the default browser; the token page should be 0600 and removed. Doable headless.
6. **e2e: `onionname set --rename-admin` on a real multisite.** The t0 stack already has an installed WordPress, so a docker-backed test could rename and log in with the new name. `rename_wp_user` is only tested against stubs; the `$wpdb` update and the `site_admins` move have never run against real WordPress.
7. **e2e: the handle-action round trips.** Write `requested-action` and its input file into the volume of a t0 node, let the daemon take it, and check the result file, its request id and the input file's removal:
   - `update`, `upload-analytics` and `refresh-status` work offline;
   - `archive-login` needs archive.org stubbed, or a bad password checked only for the file's removal.
8. **The status writer's `page_actions` against the page's check.** The census checks both sides name `archive-login`, but no test feeds a real `status_document` into the PHP gate.
9. **The poll JavaScript.** No JS is tested anywhere. A small Node or headless-browser check of the poll's handling of `archive-login`, `update` and `upload-analytics` results (success, error, request-id mismatch) would cover the notices.
10. **The menubar's setup window and the tray's GTK dialogs.** Their command lines are covered (`tests/test_menubar_actions.py`, `tests/test_setup_through_the_cli.py`, `tests/test_linux_tray_protocol.py`), but the dialogs themselves aren't. Scripting them would take the tray under Xvfb with `dogtail` or AT-SPI, or rumps with AppleScript. That is costly; the manual checklist covers it.
11. **`fetch_archive_s3_keys` against a fake archive.org.** It is tested with canned `docker exec` answers. A curl-level fake (a local HTTPS server reached through the onionheaven container) would also cover the cookie fallback path, but the real onion still needs a manual check.
